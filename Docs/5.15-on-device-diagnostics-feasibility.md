# 5.15 Experiment: on-device access to diagnostic services (feasibility note only, not built)

**Question.** Could Vitals reach the phone's own diagnostic services (the ones the Mac companion uses: battery
IORegistry with temperature, per-process CPU via DVT sysmon, syslog, crash reports) from the phone itself, by
running a local VPN loopback and using a pairing file, the way tools such as SideStore / "JIT enablers" do?

## How such tools work
1. On a computer, generate a **pairing record** for the phone (the same trust record usbmux uses) and copy it
   onto the phone.
2. On the phone, run a **packet tunnel** (`NEPacketTunnelProvider`, or a third-party "loopback VPN" app) that makes
   the device's own lockdown / RemoteXPC services reachable at a local address, as they would be from a Mac.
3. An app on the phone speaks the lockdown / RSD protocols to that address with the pairing record, starts services
   (`com.apple.mobile.diagnostics_relay`, DVT instruments, syslog relay) and reads them.

## Feasibility
- **Technically**: plausible for the lockdown-level services (diagnostics relay battery data, syslog, crash copy)
  given a valid pairing record. Developer services (DVT sysmon) additionally need Developer Mode and a mounted DDI
  and, since iOS 17, a RemoteXPC tunnel; harder and more fragile. Every iOS release can break it.
- **Effort**: a Swift implementation of lockdown + TLS + plist service protocols (or embedding a C library such as
  libimobiledevice, LGPL) plus a Network Extension target and entitlement. Weeks, with ongoing maintenance.

## App Review and policy risk (the real blocker)
- Plan §2 says **public APIs only**. Talking to lockdown / DVT is private, undocumented protocol use; Guideline 2.5.1
  (public APIs only) would apply even though no private framework is linked.
- A VPN used for anything other than a VPN service conflicts with Guideline 5.4 (VPN apps must use
  `NEVPNManager`, be offered by an organisation, and not be used to sell or collect data; using it as a local
  diagnostic transport is outside its purpose).
- Asking people to generate and import a pairing file is a sideloading-style workflow; it invites rejection and
  carries real security risk (a pairing record grants broad device access to whoever holds it).
- Likely outcome: **rejected for the App Store**. Possible for a TestFlight-only or sideloaded "pro" build, which
  conflicts with plan §9 (TestFlight then App Store).

## Recommendation
Do not build it into Vitals. Keep the Mac companion as the route to temperature and per-process data. If the maintainer wants
to explore further, do it as a separate, clearly experimental open-source tool outside the App Store app, after
the Duo has confirmed what the companion can already read. **Needs the maintainer's decision (plan §11.7).**

**Update 2026-11-15 (real Duo).** The battery registry read from the Duo over USB had no temperature key at all,
so even a working loopback would not give battery temperature on this phone. Per-process write rates (the data
that settled the real case) need Developer Mode. Both weaken the case for this experiment further.
